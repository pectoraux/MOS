## What was built

The pooled worker path — the leg of architecture.md §14's chain that MKT-011 owns: `Execution → Runtime Class (pooled-worker) → Worker`. "The default runtime uses pooled workers."

- **The dispatch command (transactional outbox).** `POST /api/executions/:executionId/dispatch` records `execution_dispatches` (ONE row per Execution identity — DB `UNIQUE (execution_id)` fence) and applies `created → queued` through the /executions single transition port with the CALLER's §8 command key. Duplicates of the same command converge (200 replayed); any different dispatch command for the same execution is a 409; sandbox-class executions are 409 (MKT-012 territory); dispatch is NEW USE (ACTIVE Workspace/Client/Agency required); dispatch is only valid from `created`.
- **The relay (outbox → durable queue).** The worker process relays `recorded` rows with `FOR UPDATE SKIP LOCKED`, submits under the cycle-scoped key `execution-dispatch:{executionId}:{cycle}` (the queue's own (queue, handler, key) fence converges re-submissions after a crash between submit and mark), then CAS-marks `submitted` with the bound `job_id`. The dispatch lifecycle is trigger-enforced: `recorded → submitted` is the only forward edge; the single backward edge is the `deferred-paused` re-arm with `cycle + 1`.
- **The pooled handler (`executions.pooled.run`).** State-driven, never sequence-driven: terminal execution → converged return (no mutation — redelivery after completion is inert); a recorded outcome without its terminal transition (crash window) applies the verdict WITHOUT re-running the task; tenant-paused executions record `deferred-paused` and complete the job (the recovery pass re-arms a fresh cycle after resume); `unknown`/`reconciling` executions are never auto-driven (reconciliation owns them). The drive to `running` uses per-cycle idempotency keys (`pooled:{dispatchId}:{cycle}:{edge}`) — job retries/redeliveries converge to the recorded transition rows (EXEC-AC-03).
- **Task runners (RUNTIME-AC-01).** Provider-neutral registry: `data.transform` (deterministic data work; content-addressed artifact; parameterizable transient failure with PROVEN-safe retry for proofs) and `api.request` (ONE bounded outbound call through the platform `HttpCallPort`: https-or-loopback, deadline, response cap; transport-refused → retryable-safe; 5xx/429 → retryable-unproven; 2xx/3xx/4xx → permanent verdict; timeout-after-send → `UnknownExternalOutcomeError`). AI-class executions ride the identical path (the execution kind is caller-declared and orthogonal) — genuine model invocation is /ai-runtime (MKT-017+) and is NOT fabricated here; this reading of "normal AI/API/data tasks" is documented as a policy decision below.
- **The §8 LOGICAL TASK key.** `deriveTaskKey` derives the task idempotency key from the task LINKAGE + dispatch input digest — never from the execution row identity — so MKT-010's retry attempt (a new execution row of the same linkage) derives the SAME key and pure runners converge to ONE content-addressed logical artifact across attempts.
- **UNKNOWN in the pooled path.** An `api.request` timeout after send transitions `running → unknown`, records the dispatch outcome `unknown`, and completes the JOB with the unknown verdict — the execution stays non-terminal and resolves only through the explicit reconciliation protocol (`unknown → reconciling → succeeded|failed|unknown`), proven end-to-end in tests.
- **Recovery (the "recovery" of "pooled task execution/retry/recovery").**
  1. *Dead-job sweep*: a dispatch whose queue job died while its execution is non-terminal and drivable is terminalized `failed` through the transition port, walking the legal machine edges with recovery-scoped idempotency keys; the §24 classification comes from the recorded job error's `retrySafe` verdict (fail-closed: only `retrySafe === true` classifies safe). `unknown`, `reconciling` and `paused` executions are never auto-failed.
  2. *Deferred-paused re-arm*: after the tenant resumes a paused pooled execution, the sweep re-arms its dispatch (`cycle + 1`) and the relay submits a fresh job.
  3. *Stale sandbox-lease release* (the automation MKT-010 documented as arriving with MKT-011): expired ACTIVE leases are released through the module's idempotent release port — which never terminalizes.
  4. *Queue stale-claim recovery*: a job left `running` by a dead worker (claim older than `MOS_QUEUE_STALE_CLAIM_MS`, default 300s, 0 disables) becomes reclaimable — re-queued when attempts remain, dead otherwise; `hasPending` treats a stale running job as pending so drain workers wait for it. Late completions from a superseded worker hit the CAS guard and are logged-and-discarded (`job.superseded`) instead of crashing the host.
- **Tenant posture.** Dispatch authorizes through `requireExecutionAccess` (agency owner/admin for the command; any active member reads the dispatch record); foreign/unknown execution ids are the uniform 404; every dispatch-plumbing field is a rejected authority field (422); audit `executions.dispatch.recorded` keyed by dispatchId (replays converge to one audit row); correlation identity is captured at dispatch time and crosses the outbox/queue boundary through durable state (OBS-AC-01 — asserted on the job row in tests).

## Policy decisions (documented, not self-invented architecture)

1. **The pooled runtime lives in `src/workers/pooled/`, NOT on the /executions module** — the MKT-010 architecture boundary (still enforced, unchanged) pins `ExecutionsModuleApi` to identity/lifecycle with no engine authority and names MKT-011 the pooled worker authority's owner. The runtime composes frozen authorities: lifecycle only through the public `transitionExecution` port, queue only through the platform `JobQueue` port; it owns exactly one table (`execution_dispatches` — the handoff record, never execution state). The static checker's known areas make `src/workers/` the sanctioned home (a new top-level `src/runtime/` would be a stray-src violation).
2. **RUNTIME-AC-01's "normal AI/API/data tasks"** — the pooled PATH is task-class-generic (registry); MKT-011 ships real `data` and `api` runners; AI-class executions ride the same path but no model invocation is fabricated (that is /ai-runtime, MKT-017+, behind its frozen boundary). Honest limitation, stated in the tests too.
3. **Outbox-before-transition ordering** (record the handoff, then apply `created → queued`): every crash window converges because the handler protocol is state-driven (a `created` execution with a recorded dispatch is driven by the handler itself; a duplicate dispatch replays and re-applies).
4. **Dispatch is NEW USE** — it hands the execution to the pooled runtime, mirroring the module's create/into-running boundary policy.
5. **§24 classification from the job error taxonomy** — `retrySafe === true` → `safe`, everything else (including `null`/absent) → `unsafe` (fail-closed, per "Non-idempotent unknown side effects must not be blindly replayed").
6. **One dispatch per Execution identity** — a re-drive after a paused/resumed cycle is the SAME dispatch row re-armed (cycle + 1), not a second dispatch; a genuinely new attempt is MKT-010's retry create + its own dispatch.
7. **The sweep may be boundary-blocked**: terminalizing a `created/queued/starting` execution must pass THROUGH `running` (the machine has no skip edges), and into-running is boundary-gated new use — a disabled boundary defers the terminalization to a later pass (the common death state, `running`, is never blocked). Documented behavior, not a silent gap.
8. **Stale-claim recovery default ON (300s)** — recovery is the point of the work item; the window far exceeds any legitimate handler duration in this codebase, and the pooled handler is convergence-safe under redelivery by contract. Existing MKT-001 queue semantics are otherwise untouched (proven by the untouched suites).
9. **`maxAttempts` on the dispatch command** (1..25, default 5) — operational attempt policy travels with the dispatch, immutable after recording.

## Honest limitations (deliberately out of scope)

- **No workflow-engine composition**: `/workflows` still does not call `/executions`; node-instance bookkeeping, task production and the engine's own retry orchestration are later work items. MKT-011 is the pooled worker authority the engine will compose.
- **No sandbox lifecycle (MKT-012)**: sandbox-class executions cannot dispatch here (409); the lease relationship and its stale-release automation are the only sandbox surface touched (both through MKT-010 ports).
- **At-least-once task execution with exactly-once logical effects**: a runner may re-run after a hard crash mid-task (before the outcome is recorded); the contract is convergence (idempotent runners, content-addressed artifacts, set-once outcomes, idempotency-fenced transitions). Runners that cannot prove effect idempotency must classify `retrySafe` false/null (fail-closed) or report UNKNOWN.
- **The deferred-paused re-arm depends on the recovery pass noticing the resumed execution** (poll cadence), not on the resume command itself; there is no resume-triggered push.
- **`api.request` idempotency against real externals** rides the `idempotency-key` header (runtime-owned, §8-derived); provider-specific idempotency semantics are integration concerns (MKT-023+).
- **No pagination** on the dispatch read surface (consistent with prior list surfaces).
- **No metrics/telemetry columns on executions** (progressive containment posture, as documented in MKT-010).
