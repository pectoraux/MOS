## What was built

The single **Evidence/provenance authority** (implementation-contract §1): the durable Evidence record with its full §13 shape, the frozen class/quality taxonomies, the explicit authorized provenance promotion, the append-oriented history with database backstops, and the supports/supersedes/contradicts reference graph — Workspace-scoped through canonical ownership resolution (Agency → Client → Workspace → Evidence).

- **The durable record (EVID-AC-01).** Every record carries the full §13 shape: source identity + source locator/reference, `retrieved_at` (server clock) and `source_observed_at` when known, provenance, evidence_class, quality_grade, content + optional immutable artifact reference, the server-computed sha256 `content_digest` (verified against the content in tests), the actor/system that collected it (`collected_by` — a server-derived principal label, never a request field), applicability scope, and the reference edges. The §3 required identifiers are present (immutable id, version CAS for the concurrent promotion path, created_at/updated_at). Verified at the API surface AND directly in the database.
- **The frozen taxonomies.** The eight evidence classes (source_fact, observation, inference, hypothesis, attribution, prediction, causal_estimate, learning) and the ordered-but-non-absolute quality grades A..F, both CHECK-constrained in the database and exported as the frozen code registries (code/SQL parity pinned by the architecture tests).
- **The class↔provenance creation pairing (EVID-AC-03's structural half).** Source collections (source_fact, observation) are born **OBSERVED** — collected through this evidence authority — while every claim class is born **PROPOSED**. A model/human/extension output can never be BORN an authoritative observation: the pairing is a BEFORE INSERT trigger (a creation rule — provenance later moves legitimately through the promotion port), so direct SQL cannot fabricate either direction. The provenance value is never accepted from a request body (authority-field rejection).
- **The explicit authorized promotion (§13: "Promotion is an explicit authorized operation; confidence scores never promote provenance").** The frozen promotion graph is **proposed → inferred → confirmed**, with `observed` and `confirmed` terminal and **no edge into `observed` from anywhere** — a claim was never collected from a source. Promotion to `inferred` additionally requires at least one supports relationship to **OBSERVED** evidence ("extension/agent outputs are claims until supported" — security-threat-model.md; an inference is "interpretation supported by observed evidence"). The command (`POST /api/evidence/:id/promote`) is owner|admin, carries a REQUIRED reason (promotion is never silent — the ledger's reason column is NOT NULL), is idempotency-fenced (same key converges to the recorded transition; key reuse for a different target is a 409) and CAS-serialized (row lock + expectedVersion). **There is no confidence field anywhere** — the static architecture test proves the token exists only inside the authority-field rejection lists.
- **Append-oriented history (EVID-AC-02).** The record's content is FROZEN — a BEFORE UPDATE trigger rejects any change to every column except provenance/version/updated_at (the promotion port). Rows are **never deleted**: an unconditional BEFORE DELETE trigger rejects DELETE for ANY row, including a fresh record with an empty ledger (the exact case the pre-fix MKT-012 cascade silently erased — the ledger-preserving delete policy applied from day one). The promotion ledger (`evidence_transitions`) and the reference graph (`evidence_relationships`) are append-only, and **no foreign key anywhere in migration 015 carries ON DELETE CASCADE**. Supersession is a NEW record that references the old one — the superseded record stays byte-for-byte unchanged (asserted: content, digest, version, provenance, retrievedAt, updatedAt).
- **The provenance ledger carries the from_provenance consistency backstop from day one** — the guarantee the MKT-009/MKT-010/MKT-012 corrections established for the other three lifecycle ledgers: a history row is the record of a decision that WAS APPLIED. The trigger resolves the evidence row `FOR UPDATE` (re-entrant under the authorized writer's row lock — the writer records the transition while the record still durably holds `from_provenance`, then moves the row, both in one transaction) and rejects fabricated history whose from_provenance does not match the durable provenance, and any history row for unknown evidence.
- **The §14 claim rules.** A claim (any of the six claim classes) must reference **≥1 supporting evidence records** at creation — enforced by the module inside the creation transaction AND by a DEFERRABLE constraint trigger at COMMIT (the authorized path writes record + relationships atomically; a direct-SQL claim insert without supports fails at commit). A causal claim (`causal_estimate`) additionally requires its **declared quasi-experimental analysis reference** (`declared_analysis_ref`), and no other class may carry one (a stable-row CHECK) — attribution evidence cannot be serialized as a causal conclusion, and the class is immutable so no record can become causal by rewriting.
- **The reference graph.** supports / supersedes / contradicts edges, append-only, same-scope fenced (both endpoints must share one agency/client/workspace — cross-tenant and cross-workspace references are rejected at the database level), no self-reference, unique per (record, target, type).
- **The scope fences.** The record's agency/client/workspace must match the durable workspace→client ownership chain (a BEFORE INSERT OR UPDATE trigger — the module derives scope through canonical `/workspaces` resolution; direct-SQL cross-scoped fabrications are rejected).
- **The API surface** (`src/api/evidence-routes.ts`): `POST/GET /api/workspaces/:workspaceId/evidence` (record = any active member; list = member), `GET /api/evidence/:evidenceId` (+ `/transitions`) member reads, `POST /api/evidence/:evidenceId/promote` (owner|admin). Authorization through `requireEvidenceAccess` (canonical evidence → workspace → client → agency resolution; uniform 404 posture for foreign/unknown/tombstoned identifiers — no traversal oracle), the `evidence` OwnerScope variant on the pipeline + audit scope mapping, and authority-field rejection on every envelope (evidenceId, scope ids, provenance, contentDigest, collectedBy, retrievedAt, version, timestamps — and `confidence` explicitly).

## Policy decisions (documented, not self-invented architecture)

1. **The provenance promotion graph is the frozen §13 language made precise** — a documented MKT-013 design decision (no evidence state machine exists in state-machines.md): proposed → inferred → confirmed; observed and confirmed terminal; no edge into observed. "Promotion is an explicit authorized operation" (§13) + "claims until supported" (threat model) + "an inference is an interpretation supported by observed evidence" (taxonomy) are the three anchors.
2. **`observed` is a collection state, never a promotion target** — a source observation is authoritative because it was collected through the evidence authority; nothing can promote a claim into that state after the fact (EVID-AC-03's machine half).
3. **Recording is member-level; promotion is owner|admin.** Capturing source observations and entering claims is day-to-day operational work (operators, the service principal/worker path, later the engine) — the class↔provenance pairing, not the role, is what keeps model/human outputs in their place. The authoritative act (promotion) requires owner|admin.
4. **The promotion gate for `inferred` requires support from OBSERVED evidence specifically** — a claim supported only by another claim cannot become an inference ("supported by observed evidence"). Chained claims remain legitimate records; they just cannot promote past proposed on claim-support alone.
5. **The pairing is a BEFORE INSERT trigger, not a row CHECK** — provenance legitimately moves to inferred/confirmed through the promotion port; a CHECK constraint would block every promotion (this was caught and fixed during verification: the first draft used a CHECK and the promotion path proved it wrong).
6. **The transition insert precedes the row move** (the established executions/sandboxes ledger discipline): the history row records the decision while the record still durably holds `from_provenance`; both writes commit or roll back together (a CAS miss rolls the ledger insert back with the transaction).
7. **`source_observed_at` is an ISO calendar date (YYYY-MM-DD)** — the platform's frozen `isoDateField` primitive (the same one goals use); stored as the midnight-UTC instant of that date. Full-precision observation timestamps are §15's metric-observation territory (MKT-014).
8. **`declared_analysis_ref` implements §14's causal guard today** — the "declared quasi-experimental analysis reference" disjunct as a durable free-form reference (an object-store analysis document key or an external analysis citation); the "Experiment reference" disjunct arrives with MKT-015 and will be validated then.
9. **The `/evidence ──→ /executions` dependency is deliberately unused by MKT-013** — the frozen §13 record shape carries no execution ownership (the architecture test pins there is no execution_id column), and /evidence must not mutate workflow/execution state. The dependency becomes meaningful when the engine/AI composition references evidence from executions.
10. **Workspace/client liveness gates recording and promotion** (the goals-module posture): a disabled workspace or client blocks new authorized use (409) without rewriting history — existing records remain readable and intact.
11. **The claim_type axis of §14 is carried by the class itself** — inference↔descriptive, prediction↔predictive, attribution↔attributional, causal_estimate↔causal; hypothesis and learning are descriptive claims to be tested / durable conclusions. No separate claim_type column is introduced in MKT-013 (the experiment model, MKT-015, owns the experiment-side claim surface where a stored type field becomes load-bearing).

## Honest limitations (deliberately out of scope)

- **No metrics/experiments/learnings surfaces** — those are MKT-014/015/016 (they relate to evidence through this module's public contract per the dependency matrix). The evidence class taxonomy admits their record classes today (`observation` payloads, `learning`-class claims) but their modules own their own records.
- **No engine/AI composition** — nothing yet auto-records evidence during execution (the worker path is exercised by the service principal through the same API surface; `/executions` still references evidence nowhere).
- **No content-addressed object-storage integration** — `artifact_ref` is a durable opaque reference (the sha256 digest of the CONTENT is always computed server-side); a convenience API that PUTs large artifacts into the object store and records the key is future polish.
- **No pagination** on the list surface (consistent with all prior surfaces).
- **The quality taxonomy is not yet extended** — the frozen A..F set is enforced as-is; the spec's "exact grade can be extended" arrives with a future Work Item if the taxonomy grows.
- **Direct-SQL claim-support enforcement is commit-time** (the DEFERRABLE constraint trigger), not statement-time — the module's in-transaction check gives the authorized path immediate, precise 422s; direct SQL sees the rejection at commit.
