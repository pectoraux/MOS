# MKT-005 — Data/runtime infrastructure and security adapters

**Work Item:** [issue #13](https://github.com/pectoraux/MOS/issues/13)
**Architecture baseline:** v1.4 (frozen); this document records implementation decisions only and does not modify any frozen document.
**Requirements:** PLAT-001, CRED-001, OBS-001, AUD-001
**Governing principle (issue #13):** *extend the existing platform authorities; do not create duplicates.*

## What was implemented

### 1. Production object storage behind the existing port (AC-04)

`S3ObjectStore` (`src/platform/objects/adapters/s3/`) implements the **unchanged MKT-001 `ObjectStore` contract** (`put`/`get`/`exists`, content-addressed keys) against any S3-compatible endpoint (AWS S3, MinIO, R2, …):

- **SigV4 request signing is implemented over `node:crypto`** (`src/platform/objects/sigv4.ts` — a pure protocol library, deliberately outside `adapters/` so the checker's adapter rules stay meaningful). There are **zero provider SDK dependencies**: the "SDKs behind adapter boundaries" rule (AC-09) is satisfied in the strongest possible form — no SDK exists anywhere in `src/`. Wire correctness is proven against a real SigV4-validating server (MinIO rejects invalid signatures with 403); determinism is locked by known-answer unit vectors plus an independent signature derivation in tests.
- The on-storage key layout (`sha256/<xx>/<digest>`) is derived from the content address, so the provider-visible layout is internal and **identical content always converges to the same object** (idempotent puts — also the retry-safety basis for AC-08).
- Failure taxonomy is explicit: network/DNS/5xx → retryable `ProviderUnavailableError` (retry-safe, because content addressing makes the operations idempotent); timeout/abort → `TimeoutError` (retry-safe); credential/permission 4xx → non-retryable `PermanentExecutionFailureError`. `get` returns `null` and `exists` returns `false` on 404 — **no fabricated success and no fabricated data**.
- Configuration is complete-or-absent: `MOS_OBJECT_STORE=s3` without every required `MOS_S3_*` setting aborts startup (fail fast).

### 2. Advisory cache/lock capabilities behind new platform ports (AC-03)

The frozen topology (architecture.md §21) lists Redis for "queues / locks / cache". The **durable queue authority remains the PostgreSQL queue** (AC-02 — asserted by an architecture test that the queue adapters directory contains only `postgres` and no queue file mentions Redis); what MKT-005 adds is the *cache/lock* capability seam:

- `src/platform/cache/contract.ts` — advisory cache port (`get`/`set`/`delete`). Documented contract: **PostgreSQL is authoritative; every consumer must be correct with the cache fully absent; failures surface as `BackendUnavailableError` (never a fabricated value, never a silent miss).**
- `src/platform/locking/contract.ts` — advisory lock port (`acquire`/`release`). Documented contract: **fail-closed** (backend outage → throw, never a fabricated lease); leases are TTL-bounded; release is owner-checked compare-and-delete; durable correctness never depends on locks (DB fences own exactly-once).
- `RedisCache` / `RedisLock` adapters speak **RESP-2 over `node:net`** (`src/platform/redis/resp/resp-client.ts`, with TLS support for `rediss://`). Zero external dependencies; the protocol client is shared by exactly the two Redis adapters (asserted by architecture test). Locks use `SET key token NX PX ttl` for atomic acquire and a Lua compare-and-delete for owner-checked release.
- **Degenerate adapters** when `MOS_REDIS_URL` is empty: `NoCache` (always-miss, writes dropped — the *correct* no-backend cache) and `UnavailableLock` (**throws** — a lock is a safety claim and must never be fabricated). This asymmetry is deliberate and documented in both port contracts.
- Adapters reconnect lazily: a Redis outage produces explicit errors; recovery is automatic once the backend returns (proven by the outage/recovery integration test).

### 3. The frozen credential boundary (AC-05, CRED-001)

- **Migration 005** creates `credential_references`: opaque identity, immutable Agency scope, optional immutable Client narrowing, normalized kind, agency-unique live label, lifecycle (`active`/`disabled`/`deleted`, terminal), version CAS, provenance. **No column can carry secret material** — only `secret_handle`, an opaque address into the secret backend (asserted structurally by architecture tests). DB triggers back immutability of identity/scope/handle/provenance and the terminal tombstone, exactly mirroring the MKT-003/004 pattern.
- **`/credentials` module**: reference lifecycle + **fail-closed, scope-checked material resolution** (`resolveCredentialMaterial`): live reference + exact agency/client scope match → material bytes; anything else (unknown, tombstone, disabled, wrong agency, wrong client) → **uniform `null`** (no existence oracle). Creation fails closed (409) when the handle does not resolve in the backend — no dangling references.
- **Platform secret port** (`src/platform/secrets/contract.ts`): **resolution-only** (`resolve`/`exists` — there is deliberately no write/delete path; provisioning is a deployment concern). The file backend models **mounted secrets** (K8s/systemd-style `<handle>.secret` files, strict handle grammar, traversal-proof, fail-closed on missing/unreadable material).
- **HTTP surface** manages *references only*: `POST/GET /api/agencies/:agencyId/credentials`, `GET /api/credentials/:credentialId`, `PATCH /api/credentials/:credentialId/status`. The serialized reference **never includes the backend handle**; material-shaped keys (`secret`, `token`, `apiKey`, …) are rejected at validation (defense in depth); **material resolution has no route at all** (asserted by architecture test). Authorization follows the established hard-boundary posture: uniform 404 for unknown/deleted/foreign references; 403 for suspended membership — the same `/agencies` membership authority, no second authorization authority (the module imports no other module; scope is carried as immutable data).

### 4. The append-only audit authority (AC-06, AUD-001)

- **Migration 006** creates `audit_events` with every §22 field (event_id, occurred_at, actor, agency/client/workspace scope, action, target type/id, correlation_id, causation_id, before/after versions, result, details). **`BEFORE UPDATE OR DELETE` triggers reject any rewrite** — the trail is immutable at the database level, stronger than API discipline. A partial unique fence on `idempotency_key` makes replayed emissions of the same logical event converge to one row.
- **`/audit` module**: `appendAuditEvent` (single INSERT, server-owned fields) + `queryAuditEvents` (read-only, server-side). The **append guard** validates action shape, correlation presence and rejects material-shaped detail keys (§21 backstop) **before** insert.
- **Emission wiring**: every mutation route's pipeline step 7 now calls `recordMutationAudit` (via `src/api/audit-emit.ts`) after its observability record and **before responding** — a material action that claims completion (the HTTP response) has already persisted its audit row; an audit failure fails the request instead of silently losing the event. Audited actions: identity (user create/profile/status, platform roles, credential issuance), authorization (login succeeded/failed, session revoked, memberships), tenancy (agencies, clients, workspaces lifecycle) and platform operations (job submission). Actor/scope/correlation are always server-derived; deterministic idempotency keys make caller retries converge.
- **No public mutation path**: `/api/audit/*` routes do not exist (asserted by architecture + integration tests); the only writer is server code through the module API.

### 5. Config + composition root

`MOS_OBJECT_STORE=s3` (+ `MOS_S3_*`), `MOS_REDIS_URL` (+ `MOS_REDIS_TIMEOUT_MS`), `MOS_SECRETS_DIR` — all validated at startup with fail-fast semantics (S3 complete-or-absent; secrets dir must exist). The composition root wires every new adapter **behind the existing platform ports** (AC-01) and constructs the `/credentials` + `/audit` modules with platform ports only.

## Policy decisions

1. **No new npm dependencies.** `pg` remains the only runtime dependency. The S3 wire protocol (SigV4 REST) and the Redis wire protocol (RESP-2) are public, stable protocols implemented over Node builtins — provider SDKs cannot leak if none exist. This also keeps `npm ci`, the external-package architecture rule and the supply-chain surface unchanged.
2. **Degenerate adapters are asymmetric by design.** A missing cache is correct (advisory capability); a missing lock is a fail-closed error (safety claim). Both behaviors are documented in the port contracts and proven by unit tests.
3. **Audit-after-mutation with pre-response ordering.** The pipeline emits (persist audit) before responding: completion claims never precede durable audit. An audit failure surfaces as a failed request (no silent loss). Same-transaction audit emission (transactional outbox) is deferred to the Work Items that own those transactions — recorded as a limitation below.
4. **Login-failure audit is best-effort with loud logging.** A failed login makes no completion claim, so the original 401 is never masked by an audit failure (which is logged at error level instead).
5. **Platform job submission is audited; platform job *completion* is not.** The job record itself is the durable execution record of platform plumbing; material business execution/workflow events arrive with the Work Items that own those authorities (MKT-010+). This keeps observability (job.succeeded) and audit (material events) cleanly separated.
6. **`secret_handle` is an address, not material.** Knowing the handle yields nothing without the secret backend and an authorized scope; the API nevertheless never serializes it (defense in depth).
7. **Frozen specs untouched.** No changes under `spec/` or `docs/implementation/acceptance-contracts/` (owner-authored territory).

## Honest limitations

- **No lease/visibility timeout in the frozen queue.** A worker killed mid-`running` leaves the job durably `running` (claimed, attempt recorded — never falsely acknowledged, never lost). Claim recovery is a queue-authority semantics change that belongs to a platform Work Item, not MKT-005; the limitation is proven and documented by the queue-authority test.
- **Audit emission is not transactional with the mutation.** The audit row is persisted after the module transaction commits but before the response; a crash in that window leaves a completed mutation without its audit row (surfaced as a failed/absent response — not silent, but possible). Transactional audit arrives with the owning modules' Work Items.
- **File-backed secret backend only.** It models mounted-secret deployments (and is what the tests provision); vault-style backends are implementation-defined behind the same port and can be added at the composition root without touching consumers.
- **The RESP client is intentionally minimal** (single connection per adapter, no pipelining/pub-sub/cluster). It serves the advisory cache/lock seam exactly; production hardening beyond that scope stays a follow-up if later Work Items need it.
- **`MOS_REDIS_URL` database index is accepted syntactically** but cache/lock keys are deployment-prefixed rather than DB-selected (documented in config).
