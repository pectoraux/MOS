# MKT-007 — Playbooks and versioning

Work Item: MKT-007 (spec/work-items.md: "implement reusable versioned
Playbooks and deployment metadata"; dependencies: MKT-006).

Requirements: PLAY-001 — "Persist versioned Playbooks that can be deployed
into Client Workspaces."

Acceptance:

- PLAY-AC-01 — published Playbook version is immutable (database +
  integration test).
- PLAY-AC-02 — Workflow execution references an explicit Playbook/Workflow
  version (contract test).

## What was implemented

Migration `008_playbooks.sql` (the only new tables):

- `playbooks` — the version CONTAINER: immutable server uuid; `agency_id`
  NOT NULL FK (immutable); optional `client_id` FK (NULL = Agency-scoped
  reusable operational IP, set = Client-scoped; immutable once set); optional
  `goal_id` FK (the "Goals produce plans/playbooks" link; immutable once
  set); name/description (CAS profile); provenance; version CAS.
- `playbook_versions` — the versioned strategy artifact: immutable
  `version_id` (the `playbook_version_id` a future Deployment pins, per
  marketing-cloud-deployment-v1.4.md); per-playbook monotonic
  `version_number` (UNIQUE-fenced with the playbook); frozen lifecycle
  status CHECK (`draft|review|published|retired`); `strategy` jsonb object
  (summary + named templates); `deployment_metadata` jsonb object (required
  Domain Packs, required Integration/Extension capabilities, runtime
  requirements, trigger configuration); provenance; version CAS.
- Triggers: playbook identity/scope/provenance immutability;
  client-within-agency scope backstop; goal-within-client scope backstop
  (goal links require Client scope); version identity immutability; and the
  PLAY-AC-01 published-immutability trigger — published content
  (strategy + deployment_metadata + identity + provenance) can NEVER
  change, the only legal transition out of `published` is the
  content-preserving `published → retired`, and `retired` rows are fully
  frozen terminal history.

Module `/playbooks` (public contract + store + module): creates
Agency-scoped and Client-scoped playbooks (canonical owner resolution
through /agencies and /clients BEFORE any write; Agency ownership of a
Client playbook is server-derived from the canonical Client owner);
optional Goal link resolved through /goals (foreign/unknown → uniform 404);
version creation with server-assigned sequential version numbers under the
playbook row lock; CAS content updates (draft/review only);
CAS lifecycle transitions through the frozen table; canonical
`resolvePlaybookOwnership`; and `getPlaybookVersion` — the EXPLICIT version
reference resolution (any lifecycle state, byte for byte, forever).

API routes (`src/api/playbooks-routes.ts`): 12 routes — agency/client
create+list, playbook read + ownership-context + CAS profile, version
create/list/read-by-explicit-id + CAS content + CAS lifecycle — with strict
authority-field rejection, `requirePlaybookAccess` (compose the SAME
/agencies membership authority after canonical ownership resolution — no
second authorization authority), and `recordMutationAudit` on every
mutation (`playbooks.playbook.created|profile_updated`,
`playbooks.version.created|content_updated|status_changed`).

## How the acceptance criteria are proven

- **PLAY-001** — playbooks-api.test.ts: Agency-scoped AND Client-scoped
  playbooks persist with explicit sequential version numbers (1..N), exact
  strategy/deployment-metadata round-trips incl. direct DB jsonb
  verification; playbooks-concurrency.test.ts: concurrent creation
  serializes to exactly 1..8 with no duplicates or gaps; the versioned
  artifact is deployable BY REFERENCE (the explicit `versionId` surface the
  Deployment authority will bind).
- **PLAY-AC-01** — playbooks-api.test.ts: content update on a published
  version → 409 AND direct DB `UPDATE strategy/deployment_metadata` →
  exception; retirement preserves content; retired rows reject everything.
  playbooks-concurrency.test.ts: DB backstops under/after races, including
  a tampering retirement attempt. Static: the published-immutability
  trigger is asserted in playbooks-boundary.test.ts.
- **PLAY-AC-02** — the contract end MKT-007 owns: every version resolves
  ONLY through its explicit identity. playbooks-api.test.ts: after v2 is
  published and v1 retired, the v1 reference returns EXACTLY v1 content
  (no floating "latest"), distinct version ids carry distinct content, a
  foreign version id is a uniform 404. Static: playbooks-boundary.test.ts
  asserts the public API exposes no `latest`/`current` floating pointer and
  no workflow/deployment/execution authority — the referencing END of the
  contract (workflow definitions pinning playbook version ids) is
  MKT-008's `WF-001` work, per the frozen dependency order.

## Policy decisions (implementation decisions within the frozen contract)

1. **Agency-or-Client ownership** follows the frozen tenant-runtime-model
   matrix row exactly ("Playbook | Agency or Client | reusable operational
   IP"): `client_id IS NULL` = Agency-scoped reusable IP (listable under
   the Agency, deployable into any authorized Client Workspace by the
   future Deployment authority); set = Client-scoped. The dependency
   matrix (/playbooks → /agencies, /clients, /goals) and PLAY-001
   ("deployed into Client Workspaces") both fit: the WORKSPACE binding is
   the Deployment's job (MKT-040), so playbooks carry no workspace scope.
2. **The version state machine is exactly the frozen machine**
   (state-machines.md): `DRAFT → REVIEW → PUBLISHED → RETIRED` — review is
   mandatory (no draft→published skip), retirement only from published, no
   back-edges. Draft AND review content stays CAS-editable (pre-publication
   states); "Published versions are immutable" is the frozen line, enforced
   by the module (409) and the database (trigger).
3. **The Playbook CONTAINER has no lifecycle status**: state-machines.md
   defines the machine for Playbook VERSIONS only. Retirement happens per
   version; the container stays addressable reusable IP. There is no
   delete/tombstone for playbooks (business objects follow MKT-006's
   append-only history decision; a Client tombstone makes Client-scoped
   playbooks uniformly unresolvable).
4. **Goal link state does not gate anything**: a terminal (achieved/
   abandoned) goal is concluded history, not a boundary — linking a new
   playbook to it is legitimate strategy work. Boundaries (Agency/Client
   liveness), not goal state, gate new use.
5. **Boundary policy mirrors MKT-006**: creating playbooks/versions,
   content edits, profile edits and PUBLICATION are new use (active
   Agency + active Client required; disabled → 409 without rewriting
   history); the editorial draft→review transition and the
   history-recording published→retired retirement stay available
   regardless of boundary state.
6. **Strategy content shape** is deliberately pre-workflow: `{summary,
   templates[{name, description?}]}` — "a versioned, reusable set of
   strategy/workflow templates" (architecture.md §8). Workflow GRAPH
   definitions are the /workflows authority (MKT-008); the playbook
   carries the strategy artifact workflow definitions are produced FROM
   (implementation-clarifications-v1.2).
7. **Deployment metadata is declarative only** (MKT-007 objective
   "deployment metadata"): requiredDomainPacks / requiredCapabilities /
   runtimeRequirements (runtime classes from the frozen compute-allocation
   list) / triggers are persisted as validated structured data. Constraint
   RESOLUTION (does the pack exist, is the capability installed, is the
   credential available) belongs to the /deployments authority (MKT-040,
   DEPLOY-002) — nothing here interprets them.
8. **Version numbers are per-playbook**, assigned server-side under the
   playbook row lock (MAX+1), UNIQUE-fenced. The opaque `version_id` is the
   primary explicit reference (what a Deployment pins); `version_number`
   is the human-visible explicit ordinal. Both are immutable.

## Honest limitations

- The referencing end of PLAY-AC-02 (Workflow DEFINITIONS and EXECUTIONS
  carrying playbook_version_id references) lands with /workflows
  (MKT-008/009) per the frozen dependency order; MKT-007 delivers and
  proves the referenced end (explicit, immutable, non-floating version
  identity + resolution contract).
- Deployment metadata names (Domain Packs, Integration/Extension
  capabilities) are validated for SHAPE only — the registries they name do
  not exist yet (/domain-packs, /integrations, /extensions are later Work
  Items); resolution is deferred to the Deployment authority by design.
- No workspace scoping on playbooks (per the frozen ownership matrix);
  workspace binding appears with Deployments (MKT-040).
- Version-list ordering is by version_number; no pagination yet (matches
  the MKT-003..006 listing convention).
