# MKT-004 — Workspace boundary: implementation record

**Work Item:** MKT-004 (issue #11) · **Architecture:** v1.4 (frozen) · **Base:** `f855ce5` (MKT-003 merged + acceptance contracts)

## What was implemented

- **Migration `004_workspaces.sql`** — `workspaces` table with server-generated immutable `workspace_id`, NOT NULL `client_id` FK (Client→Workspace ownership), `name`/`slug`, lifecycle `status` CHECK (`active|disabled|deleted`), `created_by` provenance, `version` CAS, timestamps. DB backstops (implementation-contract §25):
  - **immutability trigger** — `workspace_id`, `client_id`, `created_at`, `created_by` can NEVER be reassigned through any UPDATE path (MKT-004-AC-01; a Workspace crossing the Client boundary is structurally impossible — proven against direct DB re-parenting both cross-agency and intra-agency);
  - **deleted-terminal trigger** — tombstones never resurrect;
  - **partial unique fence** `(client_id, slug) WHERE status IN ('active','disabled')` — per-Client slug uniqueness among live workspaces, race-free under concurrent creation; tombstones do not block slug reuse (new immutable identity).
- **`/workspaces` module** (authority: Workspace ownership) — public contract (`WorkspaceRecord`, `WorkspaceStatus`, `WORKSPACE_TRANSITIONS`, `WorkspaceOwnerContext`, `composeWorkspaceOwnerContext`, `WorkspacesModuleApi`), internal store + module. Dependency matrix respected exactly: `/workspaces ──→ /clients` (the public entry imports `/clients` public only — verified by the static architecture test).
  - `resolveWorkspaceOwnership(workspaceId)` — **the canonical owner resolution** (MKT-004-AC-02): live workspace row → `/clients resolveClientOwnership` (the ONLY Client owner authority) → `WorkspaceOwnerContext` `{scope:{kind:'workspace',agencyId,clientId,workspaceId}, workspace, client, clientOwnership, resolvedAt}`, derived fresh from durable state on every call. Tombstones never resolve — workspace OR owning Client.
  - CAS lifecycle/profile mutations in row-locked transactions with the frozen transition table (`active⇄disabled→deleted`, deleted terminal).
- **6 routes** (`src/api/workspaces-routes.ts`) following the §23 pipeline (authenticate → resolve canonical owner → authorize → strict validation with forbidden authority fields → server-derived fields → execute → correlated emit → normalized result):
  - `POST /api/clients/:clientId/workspaces` (owner|admin|platform admin; Client must be active)
  - `GET /api/clients/:clientId/workspaces` (any active member of the owning agency; live workspaces only)
  - `GET /api/workspaces/:workspaceId` (member of the agency owning the workspace's CLIENT)
  - `GET /api/workspaces/:workspaceId/ownership-context` (read-only canonical owner context — AC-02 evidence surface)
  - `PATCH /api/workspaces/:workspaceId/profile` (owner|admin|platform admin, CAS; slug immutable)
  - `PATCH /api/workspaces/:workspaceId/status` (owner|admin|platform admin, CAS + transition table)
- **`requireWorkspaceAccess`** (authorize.ts): workspace → client → agency ownership resolution FIRST (uniform 404 for unknown/deleted-workspace/deleted-client), then membership authorization against the agency owning the workspace's CLIENT — the SAME durable membership authority as `requireClientAccess` (no second authorization authority, AC-08).

## Policy decisions (implementation choices within the frozen contract)

1. **Cross-tenant posture — uniform 404, one level deeper.** A caller with no membership in the agency owning the workspace's CLIENT receives the SAME `NOT_FOUND` 404 as for an unknown workspace identifier: the Client remains the hard security boundary (architecture.md §2), so foreign Workspace identifiers must not act as an existence/traversal oracle (TENANT-AC-05, MKT-004-AC-03). Rejection happens at ownership resolution — BEFORE any dependent traversal (proven by zero emitted material-mutation records and zero durable-state changes under parallel foreign probes). Intra-tenant failures stay 403 (suspended membership / wrong role), mirroring `/agencies` and `/clients`.
2. **Intra-agency cross-Client semantics.** An Agency member may address a Workspace of ANY Client of their agency by direct identifier — exactly as MKT-003 allows them to address any Client of their agency (the frozen authorization model is Agency-membership composed with the ownership chain). The Client boundary at the data level is nonetheless hard: `client_id` is immutable (DB trigger rejects re-parenting even intra-agency), per-Client slug fencing, and Client-scoped list/create routes NEVER surface another Client's workspaces.
3. **Platform administrators and the internal service principal** retain platform-operator access to Workspace routes, mirroring `requireClientAccess` semantics from MKT-003.
4. **Role model** identical to `/clients` (no new authority): create/update/lifecycle = `agency_owner|agency_admin` (+ platform operators); read/list = any ACTIVE member.
5. **Client policy over Workspaces (issue #11 security contract: "disabled/deactivated Client → Workspace access follows Client policy and cannot resurrect Client authority"):**
   - **Disabled Client:** existing workspace READS stay available (history not rewritten); workspace CREATE and profile/lifecycle-TO-active mutations → 409; shrinking transitions (disable/delete workspace) remain allowed.
   - **Deleted Client (tombstone):** `resolveWorkspaceOwnership` returns null — every workspace route is a uniform 404; workspace identifiers cannot resurrect Client authority. The workspace rows survive as history with immutable ownership.
6. **Workspace lifecycle** mirrors the frozen Client lifecycle: disable blocks new use without rewriting history; re-enable is the explicit path; delete is terminal (API replay 404 + DB trigger exception); slug reuse only by a NEW identity.
7. `created_by` is provenance only — never read for authorization.

## Honest limitations / disclosures

- No child/dependent domain objects exist yet (Goals/Workflows/Executions are later Work Items), so "denied without child/dependent lookup" is proven at the boundary itself: foreign identifiers fail at ownership resolution with zero emitted material-mutation records and zero durable-state changes. Future Workspace-scoped modules must consume `WorkspaceOwnerContext` — this is the seam.
- Client status checks inside workspace mutations are advisory policy gates read OUTSIDE the workspace row lock (same posture as MKT-003's createClient agency check); the DB immutability/terminal triggers remain the structural backstops. A Client disabled concurrently with a workspace mutation can at worst let that one in-flight mutation proceed — no ownership or lifecycle invariant can drift.
- Existence-visibility posture: foreign Workspace (any level: unknown / deleted workspace / deleted owning client / foreign owning agency) → 404 uniform (hard boundary); intra-tenant failures (suspended membership, wrong role) → 403. Deliberate and documented.
- No rate limiting on repeated 404 probes (not required by any AC; platform-level hardening item).
- Listing returns all live workspaces of the path Client; pagination/filtering is out of scope for this Work Item.
