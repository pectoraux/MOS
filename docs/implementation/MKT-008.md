# MKT-008 — Workflow graph model

Work Item: MKT-008 (spec/work-items.md: "implement typed Workflow graphs,
nodes, edges, validation and immutable deployed definitions"; dependencies:
MKT-007).

Requirements: WF-001 — "Implement one deterministic Workflow Graph
authority with typed node/edge contracts."

Acceptance (work-items.md): "graph validation, cycle/edge rules, versioning
tests." The work-item-matrix maps WF-AC-01..04 to MKT-008 for their
"definition/graph portions" only — WF-AC-01..03 concern the Workflow
INSTANCE state machine, which is MKT-009 and is deliberately absent here.

## What was implemented

Migration `009_workflows.sql` (the only new tables):

- `workflows` — the version CONTAINER: immutable server uuid;
  `workspace_id` NOT NULL FK (immutable — the scope chain ends
  Agency → Client → Workspace → Workflow); `client_id` and `agency_id`
  NOT NULL FKs SERVER-DERIVED at creation from the canonical
  /workspaces owner resolution (immutable); name/description (CAS
  profile); provenance; version CAS.
- `workflow_definitions` — the versioned typed graph artifact
  (implementation-contract §4 "A Workflow Definition is versioned and
  immutable after activation"): immutable `workflow_definition_id` (the
  "resolved workflow version reference" a future Deployment pins, per
  marketing-cloud-deployment-v1.4.md); per-workflow monotonic
  `version_number` (UNIQUE-fenced with the workflow); frozen activation
  status CHECK (`draft|review|active|retired`); optional immutable
  `playbook_version_id` FK (the "Playbook → Workflow provenance" link);
  `graph`/`input_schema`/`output_schema` jsonb objects (DB CHECK-fenced
  object tops; the full typed validation is the /workflows module
  authority); the declarative §4 policy blocks
  (`retry_policy_defaults`, `concurrency_limits`, `timeout_policy`,
  `compensation`) as CHECK-fenced jsonb; provenance; version CAS.
- Triggers: workflow identity/scope/provenance immutability; the
  scope-chain backstop (a workspace outside the recorded Client and a
  client outside the recorded Agency are rejected on INSERT/UPDATE);
  definition identity immutability (incl. the playbook provenance link);
  the playbook-provenance scope backstop (a linked playbook version must
  exist and be Agency-scoped reusable IP or belong to the workflow's OWN
  Client); and the activation-immutability trigger — ACTIVE content
  (graph, schemas, policy blocks, identity, provenance) can NEVER
  change, the only legal transition out of `active` is the
  content-preserving `active → retired`, and `retired` rows are fully
  frozen terminal history.

Module `/workflows` (public contract + pure graph validator + store +
module): Workspace-scoped workflow creation with canonical owner
resolution THROUGH /workspaces before any write and server-derived
Client/Agency ownership; version creation with server-assigned
sequential version numbers under the workflow row lock; the EXPLICIT
version reference resolution (`getWorkflowDefinition` — any lifecycle
state, byte for byte, forever); CAS content updates (draft/review only)
and CAS lifecycle transitions through the frozen table; canonical
`resolveWorkflowOwnership` (workflow → workspace → client → agency; a
tombstoned boundary never resolves); and the optional playbook-version
provenance link resolved through /playbooks' explicit version reference
(unknown/cross-Client-scope versions → uniform 404).

The pure graph validator (`internal/workflow-graph.ts`) is the authority:
every create and every content update runs the exhaustive typed-graph
validation (the frozen §4 MUST list), producing a complete deterministic
problem list:

- **typed node contracts** — the frozen architecture.md §10 class list
  (function, ai_task, extension_capability, api_action, browser_task,
  human_task, approval, experiment, condition, join, loop, terminal);
  retry/timeout/idempotency/execution-policy are executable-node
  concerns only; the human approval requirement is mandatory on
  human_task/approval and forbidden elsewhere; the join contract belongs
  to join nodes and the bounded loop contract to loop nodes; control
  nodes (condition/join/loop) consume no inputs; every node declares an
  object output schema;
- **edge legality** — the frozen §4 edge types (success, failure,
  conditional, join); conditional edges require predicate references and
  other edges must not carry one; failure edges originate only at
  executable nodes; terminal nodes have no outgoing edges; condition
  nodes express every outgoing edge as conditional (≥2 branches); one
  edge per ordered node pair; self-iteration only on loop nodes;
- **join semantics / impossible joins** — every edge into a join is a
  join-type edge mirroring the declared semantics; the declared
  predecessor set exactly equals the join-edge sources; ≥2 distinct
  predecessors; satisfiable thresholds; predecessors reachable from the
  entry (an unreachable predecessor can never release the join);
  convergence with downstream flow on a non-join/non-loop node is an
  implicit join and rejected (terminal outcome recorders are exempt —
  sinks record every arrival, §5: workflow outcomes derive from terminal
  node outcomes);
- **explicit bounded loops / cycle rejection** — every cycle must pass
  through a `loop` node declaring its iteration/termination contract
  (formalized: the graph with all loop nodes removed must be ACYCLIC —
  any cycle avoiding every loop node is rejected); the hard iteration
  bound is 1..10,000; predicate termination requires a predicate
  reference; a loop construct has exactly ONE external entry (other
  incoming edges must be iteration returns from inside its own cyclic
  region);
- **dangling nodes/edges and determinism of start** — exactly ONE entry
  node exists (parallel starts are fan-out from the single entry —
  explicit, visible, join-able), every node is reachable from it, at
  least one terminal exists, and every non-terminal node has an outgoing
  edge;
- **resolved schema mappings** — workflow-input mappings must reference
  declared top-level input-schema properties; node-output mappings must
  reference an existing ANCESTOR node and a declared top-level property
  of its output schema.

API routes (`src/api/workflows-routes.ts`): 10 routes — workspace
create+list, workflow read + ownership-context + CAS profile, definition
create/list/read-by-explicit-id + CAS content + CAS lifecycle — with
strict authority-field rejection, `requireWorkflowAccess` (compose the
SAME /agencies membership authority after canonical ownership resolution —
no second authorization authority), and `recordMutationAudit` on every
mutation (`workflows.workflow.created|profile_updated`,
`workflows.definition.created|content_updated|status_changed`).

- **Cycle/edge rules** — the illegal-cycle-without-loop, cycle-inside-a-

  individually; the architecture suite pins the frozen node/edge class
  lists and the closed public surface.
- **Versioning tests** — sequential server-assigned version numbers
  (1..N, direct DB count), the UNIQUE fence visible as a real PostgreSQL

  profile), the explicit version reference resolving retired content
  byte-for-byte with no floating latest (structurally asserted: no
  latest/current pointer exists anywhere), foreign definition ids as
  uniform 404s, and activation-immutability at the API (409) AND the

- **No runtime state** — the definition status CHECK and the code
  transition table carry no instance states (running/paused/ready/

  no instance/run/execution concepts; the routes register only
  definition-management paths; MKT-001..007 regressions all green
  (188→247 unit, 62→71 architecture, 192→219 integration).

## Policy decisions (implementation decisions within the frozen contract)

1. **The versioned unit is the Workflow Definition** (implementation-
   contract §4 field list: workflow_definition_id + version +
   workspace/client owner + …). The `workflows` table is the container
   (name/description profile); each `workflow_definitions` row IS one
   definition version pinned by its explicit `workflow_definition_id`.
2. **Workspace-scoped ownership** (tenant-runtime-model "Workflow |
   Workspace/Client"): the workflow carries a REQUIRED workspace_id;
   client_id and agency_id are server-derived from the canonical
   /workspaces owner chain and DB-backstopped on both hops. The frozen
   dependency matrix gives /workflows no direct /clients or /agencies
   dependency, so the owner context composes exactly the rows the
   /workspaces authority resolves (indexed types, no forbidden imports).
3. **The activation state machine** (`draft → review → active → retired`)
   implements §4's "activation state"/"immutable after activation" using
   the same family shape as the frozen Playbook Version machine, with
   the freeze point renamed to the frozen contract's own word
   (`active`). Review is mandatory before activation; retirement only
   from active; retired is frozen terminal history. The frozen
   state-machines.md defines NO definition machine — the Workflow
   INSTANCE machine (DRAFT → READY → RUNNING → …) is MKT-009 and is
   deliberately not expressible here.
4. **Activation requires a PUBLISHED playbook version** (when linked):
   draft/review playbook versions are CAS-editable, so an immutable,
   deployable-by-reference workflow definition must never rest on one.
   At link time any existing playbook version is accepted (definitions
   and playbook versions co-evolve while editable); at activation the
   pinned version must be `published`. A retired/draft pinned version
   blocks activation (the operator links the successor in a NEW
   definition version).
5. **Route validation is the envelope, the module is the graph
   authority**: routes enforce types/bounds/authority-field rejection
   and the graph object shape; the exhaustive typed-graph validation
   (the frozen §4 MUST list) runs once, inside the /workflows module, on
   every create and content update — whatever the caller did upstream.
6. **Predicate and policy references are shape-validated only** (non-
   empty strings): the /policies registry they name does not exist yet;
   resolution is deferred exactly like MKT-007's declarative deployment
   metadata.
7. **One entry node** (deterministic start): parallelism is fan-out from
   the single entry — explicit, visible and join-able; a disconnected
   component is a dangling structure and rejected. Terminal outcome
   recorders are exempt from the implicit-join rule (sinks record every
   arrival; no downstream release decision exists).
8. **Graph bounds** (≤200 nodes, ≤500 edges, join predecessors ≤50,
   iteration bound ≤10,000, mapping fields ≤50, schema properties ≤100):
   bounded graphs keep validation deterministic and cheap.
9. **Boundary policy mirrors MKT-006/007**: creation, content edits and
   ACTIVATION are new use (ACTIVE workspace + client + agency required;
   disabled → 409 without rewriting history); the editorial
   draft → review transition and the history-recording active → retired
   retirement stay available regardless of boundary state.
10. **No delete/tombstone for workflows** (append-only history follows
    MKT-006/007); a workspace tombstone makes every workflow route a
    uniform 404.

## Honest limitations

- The Workflow INSTANCE state machine, run/execution semantics and the
  /executions authority are MKT-009/MKT-010 — nothing here creates,
  starts, pauses or observes runtime state (structurally asserted).
- Deployment binding (workspace activation, dependency resolution,
  rollback) is MKT-040; the definition is deployable BY REFERENCE (the
  explicit workflow_definition_id surface) but nothing binds it yet.
- Predicate references, execution policy references and compensation
  declarations are shape-validated data; their registries and runtime
  interpretation arrive with later Work Items.
- Join release semantics beyond structural satisfiability (e.g. full
  dataflow deadlock analysis inside cyclic regions) are runtime
  concerns; the definition level proves reachability, exact predecessor
  sets and threshold bounds.
- No pagination on listing surfaces (matches the MKT-003..007
  convention).
