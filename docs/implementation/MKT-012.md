## What was built

The runtime ENVIRONMENT authority of the chain the work order fixes — `Execution → Runtime Class → Sandbox → Lease → Worker / task execution` — established on the ONE authoritative runtime allocation boundary (implementation-clarifications-v1.2.md "Runtime authority": sandbox objects are Workspace/Client scoped, but their lifecycle and lease records are governed through the execution/runtime contract exposed by `/executions`; no second runtime engine).

- **The Sandbox identity (RUNTIME-AC-02 as superseded).** The immutable identity tuple is exactly `sandbox_id + client_id + workspace_id + runtime_class + environment_identity` — the table has NO `execution_id` column (implementation-contract-v1.2.md §1: "The Sandbox entity MUST NOT contain execution_id as an ownership field"). The scope is server-derived from the canonical Workspace owner and DB-backstopped (the scope-chain trigger rejects a cross-scoped row). Ephemeral sandboxes are execution-scoped through the LEASE, never through identity; their `environment_identity` is a server-generated nonce (a caller-supplied one is a 422) — an ephemeral environment is never reused. Persistent/dedicated environments are caller-named and REUSABLE: the live-environment partial UNIQUE fence admits ONE live sandbox per `(workspace, runtime_class, environment_identity)` (a failed or released environment may be re-provisioned as a NEW row).
- **The frozen 8-edge lifecycle** (state-machines.md "Sandbox", reaffirmed by state-machines-v1.2.md): `REQUESTED → PREPARING → READY`, `PREPARING → FAILED | CANCELLED`, `READY → RELEASING | CANCELLED`, `RELEASING → RELEASED`, `CANCELLED → RELEASED`. Terminal states: FAILED and RELEASED; CANCELLED is deliberately NOT terminal (its only forward edge is RELEASED — teardown still runs), and REQUESTED's only forward edge is PREPARING (there is no prepare-less cancel — the frozen machine's drawn shape, pinned by unit + SQL tests). Enforced in code AND in the database (machine trigger: illegal edges, terminal immutability, and the entering-edge payload evidence — descriptor at ready, failure reason at failed, released_at at released).
- **The append-only transition ledger** (`sandbox_transitions`): `(sandbox_id, idempotency_key)` UNIQUE (the §8-class command fence per edge), legal-pair-checked with the to-failed-requires-reason payload contract, append-only, and — applying the MKT-010 audit-erratum lesson from day one — from_status-consistent with the sandbox row (the history trigger resolves the row `FOR UPDATE` and rejects fabricated applied transitions, even under direct SQL).
- **The state-driven protocol operations** (idempotent convergence commands, like the MKT-011 pooled handler): `prepareSandbox` (requested → preparing → driver → ready|failed; the driver is invoked OUTSIDE the row-lock transactions; any driver failure settles FAILED fail-closed), `cancelSandbox` (the frozen cancel edge + teardown completion), `releaseSandbox` (ready → releasing → teardown → released; also completes CANCELLED and re-drives crash-window RELEASING sandboxes). Every edge is a recorded, keyed transition; re-invocation after a crash between the recorded edges converges on the SAME sandbox (proven deterministically with legal-edge SQL fabrications of both crash windows). Provisioning carries the §8 command key with a provision fingerprint (the ephemeral nonce is excluded from the digest so replays converge), is NEW USE (ACTIVE boundaries required), and converges duplicate keys and same-environment re-provisions to the ONE live sandbox.
- **The declared runtime contract.** `concurrency_contract` is an immutable sandbox attribute — `exclusive` (the default strict v1.2 invariant) or `concurrent-safe` (the dedicated-runtime shape that "explicitly permits safe concurrent use"). The lease table RECORDS the contract at acquisition (server-derived from the sandbox row, immutable after acquisition — migration 013 backfills `exclusive`, the invariant every pre-MKT-012 lease was created under), and the one-active-controller partial UNIQUE index is CONTRACT-SELECTED: at most one active lease per EXCLUSIVE sandbox; a concurrent-safe sandbox may hold multiple active leases (each execution still holds at most one active lease at a time).
- **The sandbox-validated lease.** `acquireExecutionSandboxLease` now validates the sandbox side (with the migration-013 DB trigger as backstop): the sandbox must EXIST, be READY, share the execution's client and workspace ("Cross-client sharing is forbidden"), and be of the SAME runtime class as the execution's declared class — the execution's runtime class names the environment class it needs, so an ephemeral-class execution cannot lease a persistent environment and vice versa.
- **The teardown gate.** A sandbox cannot enter RELEASING, CANCELLED or RELEASED while an ACTIVE lease controls it (module pre-check + DB trigger): leases are released first — by the owning execution or through the deterministic stale-lease reclamation (MKT-010's port, MKT-011's sweep) — and only then is the environment torn down. Releasing a sandbox NEVER terminalizes or transitions any Execution (asserted end-to-end).
- **The provider-neutral driver port.** `SandboxDriver` (`src/platform/sandboxes/driver.ts`) with the default in-process SIMULATED substrate adapter wired at the composition root (mirroring `HttpCallPort` + `FetchHttpCall`): `prepare` fails closed on unsatisfiable capabilities (an unsatisfiable provisioning request is a provisioning failure — never a silent capability downgrade) and returns the opaque resource descriptor (the runtime resource state); `teardown` is idempotent and handles the never-ready null-descriptor path. The driver is NEVER an authority — it holds no state, writes no rows, and the module interprets its outcomes.
- **The API surface** (`src/api/sandbox-routes.ts`, registered on the router): `POST/GET /api/workspaces/:workspaceId/sandboxes` (provision is owner|admin command — NEW USE; list is member read), `GET /api/sandboxes/:sandboxId` (+ `/transitions`, `/leases` — member reads), `POST /api/sandboxes/:sandboxId/{prepare,cancel,release}` (owner|admin commands). Authorization through `requireSandboxAccess` (canonical sandbox → workspace → client → agency resolution; uniform 404 posture), the `sandbox` OwnerScope variant on the pipeline + audit scope mapping, and authority-field rejection on every envelope — INCLUDING the credential-shaped names (`credentials`, `secrets`, `token`, `apiKey`, `password`, …), the behavioral half of RUNTIME-AC-03 next to the static proofs (no credential-shaped column in the schema, no credential material on the driver surface).

## The seven §5 verification tests (implementation-contract-v1.2.md)

1. **Same workspace, separate executions → same persistent sandbox reused sequentially** — `§5.1` test: execution A leases, releases; execution B leases the SAME sandbox; distinct leases, distinct identities; both executions keep status `running` and version 4 through the ENTIRE sandbox lifecycle (also the RUNTIME-AC-04 proof).
2. **Separate clients → persistent sandbox cannot be shared** — `§5.2` test: the same environment name in a foreign workspace provisions a DISTINCT sandbox; a foreign execution leasing across scope is a 409 (`cross-scope leasing is forbidden`); unknown sandbox ids are uniform 404s; malformed ids are 422s; runtime-class mismatches are 409s.
3. **Concurrent lease acquisition → exactly one permitted controller** — `§5.3` test: two executions race an EXCLUSIVE sandbox — one 201, one 409; and the CONCURRENT-SAFE contract permits both to hold ACTIVE leases simultaneously (two active lease rows asserted in SQL) while one-active-per-execution still holds.
4. **Stale lease recovery → deterministic convergence** — `§5.4` test: an already-expired lease blocks the gated sandbox release (409) until the idempotent reclaim releases it, then the release converges; the execution is never terminalized. (The MKT-011 worker-sweep automation of the same reclaim remains proven in the pooled suite, now against a real sandbox.)
5. **Sandbox release does not mutate workflow state** — `§5.5` test: a REAL workflow instance (definition walked to active, instanced) keeps its exact status, version and EMPTY transition history across the full sandbox lifecycle.
6. **Unknown external execution → no automatic duplicate side effect** — `§5.6` test: a sandbox-class execution going `running → unknown` triggers NOTHING automatic — no execution transitions, the lease stays active, the sandbox stays ready, no new leases or sandboxes; the explicit release and reconciliation paths still work.
7. **Reconciliation paths preserve one Execution identity** — `§5.7` test: `unknown → reconciling → succeeded` (with evidenceRef) on ONE identity while leased — the lease survives reconciliation (an Execution-authority decision orthogonal to the runtime relationship), and the explicit release follows.

Plus: the RUNTIME-AC-01 pooled path remains green (the untouched MKT-011 suites), and every lease fixture across the MKT-010/011 suites now provisions REAL sandboxes — the lease-contract trigger validates existence/scope/class/contract on every lease INSERT, direct SQL included.

## Policy decisions (documented, not self-invented architecture)

1. **The sandbox authority lives on the `/executions` module — there is no `/runtime` or `/sandboxes` module.** implementation-clarifications-v1.2.md "Runtime authority" names `/executions` the authoritative runtime allocation boundary; the frozen module dependency matrix has no runtime row; the architecture tests pin that no second runtime engine module exists and that the `/executions` public contract still carries no engine authority.
2. **REQUESTED cannot be cancelled** (no `requested → cancelled` edge exists in the frozen machine): a requested sandbox is prepared first (which settles ready or failed) and then cancelled/released. Refused with the precise frozen-machine reason, pinned by tests.
3. **CANCELLED is not terminal** — its only forward edge is RELEASED, so every cancel drives (or leaves recoverable) the teardown completion; `releaseSandbox` also completes a CANCELLED sandbox (the machine's two teardown paths converge).
4. **The runtime-class match between execution and sandbox** — the frozen compute-allocation model means the execution's `runtimeClass` names the environment class it needs; the lease must match (DB-backstopped).
5. **The reuse convergence does not consume the §8 key** — a second provisioning of the same LIVE environment converges to the existing sandbox without recording a row; the key was never attached to that row (a later different command may still use it). A terminal (failed/released) environment is re-provisioned under the same identity as a NEW row.
6. **Provisioning is NEW USE; the lifecycle protocol commands are not** — provisioning allocates resources (ACTIVE boundaries required, mirroring execution create/dispatch); prepare/cancel/release are bookkeeping/completion commands available regardless of boundary state (mirroring the execution transition posture: history keeps recordable, cancellation never blocked).
7. **The in-process driver is a SIMULATED substrate** — it proves the entire lifecycle protocol and the fail-closed capability semantics against the real authority and DB backstops; real isolation substrates (process isolation, browser pods, micro-VMs — ADR-0004's AWS-class role) are later composition-root adapters behind the same port. The capability model ('browser', 'filesystem', 'process' supported) makes unsatisfiable capabilities deterministic provisioning failures.
8. **Sandbox lifecycle command keys are bounded to 100 characters** because the protocol ops derive per-edge ledger keys (`sbxprep:{sandboxId}:{key}:settle`, …) that must fit the 200-character transition-key bound.
9. **The migration-013 lease upgrades amend migration 011's table without touching the checksummed 011 file** — additive `ALTER TABLE` + trigger + index replacement in 013 only (the index keeps its name: it is still the v1.2 backstop against two conflicting active controllers, now contract-aware).

## Honest limitations (deliberately out of scope)

- **No real isolation substrate**: the default driver is an in-process simulation (lifecycle bookkeeping, not OS/browser isolation); no credentials are injected anywhere yet — policy-driven just-in-time credential injection arrives with the policy engine integration (MKT-021, `/executions ──→ /policies` is already in the frozen matrix; POL-001 governs). RUNTIME-AC-03's "policy-scoped" half is therefore structural + behavioral today (no credential fields anywhere; credential-shaped inputs rejected; static tests pin it), with the policy evaluation itself future work.
- **No workflow-engine or AI-provider composition**: `/workflows` still does not call the sandbox surface; nothing auto-provisions a sandbox for a sandbox-class execution at dispatch time (MKT-011's dispatch still 409s sandbox-class executions — the composition is the engine work item). Workflow orchestration and AI routing stay OUT of the sandbox layer, per the work order.
- **No sandbox automation in the worker**: lease reclamation is automated (MKT-011's sweep); sandbox provisioning/teardown is command-driven (the idempotent, recoverable protocol ops ARE the recovery mechanism). An auto-release policy for orphaned ephemeral sandboxes ("normally released after the Execution reaches a terminal/reconciled state" — the word is "normally", i.e. policy) is future runtime policy.
- **At-least-once driver semantics**: `prepare` may run more than once across crash windows (the driver contract requires idempotence per environment); a concurrent settle that wins a prepare race discards the loser's handle (state-driven convergence). Teardown failure leaves the sandbox CANCELLED/RELEASING and propagates the error — a retry converges (the in-process driver never fails teardown, so that specific retry path is covered by the crash-window SQL fabrications, not by a failing-teardown driver).
- **The record-only history residual** (same as executions, documented there): a direct-SQL ledger row with a MATCHING from_status records without the row having moved — the predicate is consistency, not a writer ban.
- **The MKT-009 workflow-instance history-ledger backstop remains deliberately untouched** — it is the Architect's separately-scoped corrective Work Item and is NOT folded into MKT-012.
- **No pagination** on the list surfaces (consistent with prior surfaces).
