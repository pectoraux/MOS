## What was built

production-style into the existing MKT-001 platform (real PostgreSQL, real
HTTP subprocesses — no mocks):

### Key mechanics

- **Dependency-matrix compliance** (module-dependency-matrix.md):
  `/auth → /users` (login/session validation resolve user identity through the
  users public contract — never raw SQL over users tables);
  `/agencies → /users` (owner/member resolution); platform ports only
  (`Db`, `Clock`, `IdGenerator`) injected at the composition root.
- **Stable platform principal**: authentication resolves
  `{kind:'user', userId, email, displayName}` from durable state on every
  request — principals carry NO roles. Authorization is resolved per-operation
  (fresh DB reads), so it can never ride on a stale claim.
- **Credentials stay behind /auth** (issue #6 data contract): raw passwords
  and tokens are never persisted. `auth_credentials.verifier` is a scrypt hash
  (`scrypt$N$r$p$salt$hash`, constant-time verify, fail-closed on malformed
  verifiers); `auth_sessions.token_hash` is SHA-256 of an opaque 256-bit
  token. The raw token is returned exactly once at login. The `/users` domain
  records contain no credential material.
- **Membership model (AC-02)**: `agency_memberships` rows carry explicit
  `membership_id`, `agency_id`, `user_id`, `role`, `status`
  (active/disabled/revoked), `version` (CAS) and `revoked_at`.
  - duplicate creation DB-fenced: partial unique index
    `(agency_id, user_id) WHERE status IN ('active','disabled')` +
    `ON CONFLICT DO NOTHING` → 409;
  - revoked is TERMINAL: frozen transition table in code + DB trigger
    backstop;
  - concurrent updates converge: row `FOR UPDATE` + explicit version check →
    exactly one winner per version (409 for the loser), no lost updates;
  - the last active `agency_owner` can never be demoted/disabled/revoked
    (owner-row locks make the invariant race-free; the pathological
    simultaneous demotion of the last two owners maps the PG deadlock to a
    retryable ConflictError).
- **Role model (AC-03)**: exactly the frozen initial set, represented in the
  two canonical registries — platform roles (`platform_administrator`,
  `platform_developer`) attach to USER identity; agency roles (`agency_owner`,
  `agency_admin`, `agency_operator`, `client_collaborator`, `human_agent`)
  attach to MEMBERSHIP rows. Role assignment is structurally orthogonal to
  tenant ownership: `agencies` has NO owner column and `users` has NO role
  column — enforced by a static test against the actual migration.
- **Canonical authorization context (AC-04)**:
  `resolveAuthorizationContext(userId)` composes durable user + platform
  roles + memberships into the canonical context
  (`{principal, platformRoles, memberships[], resolvedAt}`) — the shape
  MKT-003 (Client authorization) and MKT-004 (Workspace authorization)
  extend. Exposed read-only for the caller's own principal at
  `GET /api/auth/authorization-context`; enforcement is per-route
  server-side and never trusts this output or any client claim.
- **Fail-closed identity (AC-05)**: disabled user → sessions revoked at
  disable time AND user-status re-checked on every authentication;
  credential replacement revokes all sessions; revoked/disabled memberships
  lose agency access on the very next request; login failures are uniform
  401s (no account enumeration).
- **Bootstrap administrator**: optional, explicit, both-or-neither config
  (`MOS_BOOTSTRAP_PLATFORM_ADMIN_EMAIL`/`_PASSWORD`). Idempotent at startup —
  an existing user is never duplicated or reset. Only the scrypt verifier is
  persisted.
- **§23 pipeline discipline everywhere**: mutations use
  `defineMutationRoute` (authenticate → resolveOwner → authorize → validate →
  derive+execute → emit → respond). The one exception is documented inline:
  `POST /api/auth/login` IS the authentication boundary (there is no prior
  principal); it still enforces strict validation with authority-field
  rejection, server-derived fields only, and emits a correlated
  `auth.session.created` record.

## API surface

```text
POST   /api/auth/login                          email+password → session token
POST   /api/auth/logout                         revoke presented session
GET    /api/auth/authorization-context          canonical context (self)
POST   /api/users                               create identity (platform admin|service)
GET    /api/users/:userId                       read (self | platform admin | service)
PATCH  /api/users/:userId/profile               rename (self | admin; CAS)
PATCH  /api/users/:userId/status                disable/enable (platform admin; CAS; revokes sessions)
POST   /api/users/:userId/credential            provision/replace password (platform admin)
POST   /api/users/:userId/platform-roles        grant platform role (platform admin)
DELETE /api/users/:userId/platform-roles/:role  revoke platform role (platform admin)
POST   /api/agencies                            create agency + founding agency_owner (platform admin)
GET    /api/agencies/:agencyId                  read (active member | platform admin | service)
PATCH  /api/agencies/:agencyId/profile          rename (owner/admin | platform admin; CAS)
PATCH  /api/agencies/:agencyId/status           lifecycle (platform admin; CAS)
GET    /api/agencies/:agencyId/memberships      list (active member | platform admin | service)
POST   /api/agencies/:agencyId/memberships      add member (owner/admin | platform admin)
PATCH  /api/agencies/:agencyId/memberships/:membershipId  role XOR status (owner/admin | platform admin; CAS)
```

MKT-001 routes (`/api/platform/*`) are unchanged and still require the
internal service principal.

## Environment limitations and scope disclosures (honest)

- **No external IdP/OAuth/SSO**: provider-neutral credential/session contracts
  only (scrypt + opaque bearer sessions), per the issue's "out of scope unless
  required solely as an adapter seam" rule. The `/auth` module boundary is the
  seam where an external identity provider adapter would later be wired (at
  the composition root) without touching domain modules.
- **No login rate limiting / lockout** in MKT-002 (not part of any acceptance
  criterion; flagged for a later security hardening Work Item). The uniform
  401 behavior at least avoids account enumeration.
- **User email is immutable** after creation (identity anchor; rename is
  self-service, email changes are an account-recovery flow that does not
  exist yet).
- **Existence visibility**: unknown agency → 404, existing-but-forbidden
  agency → 403 for authenticated users. Agency existence is treated as
  non-secret at the platform-user level (agencies are commercial tenants;
  the HARD isolation boundary is the Client, MKT-003). If the architect
  prefers uniform 404s, this is a one-line change in `requireAgencyAccess`.
- **`created_by` on agencies** is server-derived provenance (the creating
  platform administrator), informational only — it is never read for
  authorization (ownership is the membership role).
- **Last-owner guard deadlock disclosure**: two transactions simultaneously
  demoting the last TWO active owners of the same agency can trigger a
  PostgreSQL deadlock (lock-ordering cycle). PG's deadlock detector aborts
  one; the module maps this to a retryable `CONFLICT` (409). The invariant
  (never zero active owners) is preserved in every interleaving.
- **Bootstrap password material** transits process configuration at startup
  only and lands as a scrypt verifier; it is never written to logs or
  observability records (`identity.bootstrap.created` logs the email only).
- **Client/Workspace authorization is NOT implemented** (MKT-003/MKT-004):
  `resolveAuthorizationContext` deliberately stops at agency memberships, and
  no client-scoped traversal exists anywhere in this change.
