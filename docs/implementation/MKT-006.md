# MKT-006 — Goals domain

**Work Item:** MKT-006 (Goals domain; dependencies: MKT-004; issued in the owner's work order — "Z.ai should implement issue #13 only" was MKT-005; MKT-006 is issued by the owner message that opened this cycle)
**Architecture baseline:** v1.4 (frozen); this document records implementation decisions only and does not modify any frozen document.
**Requirements:** GOAL-001
**Acceptance:** GOAL-AC-01..02
**Governing principle:** the Goal is the **business-objective authority** everything downstream (Playbooks → Workflows → Execution → AI Runtime) will reference — with **no Workflow/Playbook/Execution authority introduced here** (architecture.md §7: "Goal is not a workflow").

## What was implemented

### 1. The Goal data model (GOAL-001)

**Migration 007** creates `goals` (the only new table — asserted by architecture test):

- **Immutable identity** (`goal_id`, server-generated UUID, trigger-enforced) + **Client ownership** (`client_id`, NOT NULL FK, trigger-enforced immutable — a Goal can never cross the Client hard boundary, GOAL-AC-02 at the storage layer).
- **Client / Workspace scope**: `workspace_id` is an OPTIONAL FK to `workspaces` (NULL = client-wide goal). It is **immutable once set** (scope is durable identity — re-scoping requires a NEW goal, never a silent migration), and a dedicated trigger (`goals_workspace_within_client`) rejects any workspace that does not belong to the goal's Client on INSERT/UPDATE — the boundary cannot be crossed through the scope column even if every application check were bypassed.
- **Objective** (text, 1..2000), **measurable success criteria** (`success_criteria` jsonb, **CHECK non-empty array** — a Goal cannot even be persisted without criteria; each criterion binds a named metric to a numeric target through an explicit comparator `>= | > | <= | < | ==` — measurability is structural, not prose, GOAL-AC-01), **metrics** (additional observed metrics, jsonb array), **constraints** (`resource | risk | time | other`, jsonb array), **time horizon** (`{startsOn, endsOn}` ISO calendar dates, jsonb object or NULL).
- **Lifecycle**: `draft → active → achieved|abandoned`, `draft → abandoned`; `achieved`/`abandoned` are TERMINAL and a **DB trigger freezes every content-changing UPDATE on terminal rows** (business history is append-only). There are deliberately **no execution semantics** (no pause/resume/running — those belong to Deployments/Workflows in later Work Items).
- **Provenance** (`created_by`/`created_at`, trigger-enforced immutable; ownership is server-derived — callers cannot supply any authority field) and **version/CAS** (row-locked CAS transitions, exactly the MKT-003/004 pattern).
- **No uniqueness fence** (deliberate): Goals are append-oriented business records; two goals may carry identical content. Concurrent creation is serialized by server-generated identity (proven by the concurrency test), and mutation safety comes from CAS.

### 2. The `/goals` module (`src/modules/goals`)

Dependency matrix honored exactly: `/goals ──→ /clients, /workspaces` (asserted by architecture test + arch-check). The module:

- resolves the owning Client **through `/clients resolveClientOwnership`** and the optional Workspace scope **through `/workspaces resolveWorkspaceOwnership`** — it never re-derives ownership (implementation-contract §2: canonical owner before dependent traversal);
- `createGoal`: canonical Client resolution first (tombstone → 404, disabled → 409); workspace scope resolution second — **unknown, tombstoned, or foreign-to-this-Client workspace → uniform 404** (no existence oracle); disabled workspace → 409; measurability asserted at the authority boundary (`assertMeasurableCriteria`) in addition to route validation and the DB CHECK;
- `resolveGoalOwnership`: goal → Client (canonical) → Agency + workspace row composed into the **GoalOwnerContext**; a tombstoned Client never resolves (uniform 404). A tombstoned Workspace leaves the Client-owned goal **readable** (deleting an organizational boundary does not erase business history); workspace liveness/activeness gates NEW use only;
- `updateGoalContent` / `setGoalStatus`: row-locked CAS + frozen `GOAL_TRANSITIONS` table; **activation and content edits are "new use"** (require active Client and, when scoped, active Workspace — a Goal may never resurrect disabled-boundary authority); **terminal transitions remain available under disabled boundaries** (recording history is never blocked);
- `listGoalsForClient`: ALL lifecycle states (terminal goals are visible business history, not tombstones).

### 3. HTTP surface (`src/api/goals-routes.ts`)

```
POST   /api/clients/:clientId/goals          create (agency_owner|agency_admin|platform admin|service)
GET    /api/clients/:clientId/goals          list all states (any active member)
GET    /api/goals/:goalId                    read (member of the owning agency)
GET    /api/goals/:goalId/ownership-context  canonical owner context (read-only evidence surface)
PATCH  /api/goals/:goalId/profile            CAS content update (owner|admin|platform admin|service)
PATCH  /api/goals/:goalId/status             CAS lifecycle transition (owner|admin|platform admin|service)
```

- Every route follows the §23 pipeline: authenticate → resolve canonical owner → authorize → validate → execute → emit → respond. `requireGoalAccess` (in `authorize.ts`) resolves goal → client → agency ownership **before** the membership check; non-members get the **same 404 as an unknown goal** (GOAL-AC-02: no traversal/existence oracle, rejection before dependent traversal); suspended members get 403; the authorization authority remains exactly `/agencies` memberships — **no second authorization authority**.
- Strict validation: authority fields (`goalId`, `clientId`, `agencyId`, `status`, `version`, `createdBy`, `createdAt`, `updatedAt`, and `workspaceId` on mutations) are rejected; criteria items are strict objects (unknown keys rejected, comparator enum, finite numeric target); time horizon dates must be real calendar dates; `endsOn >= startsOn`.
- Audit: `goals.goal.created|profile_updated|status_changed` events with goal-scoped owner (agency/client/workspace), CAS versions, deterministic idempotency keys and the request correlation id — emitted before the response (MKT-005 ordering guarantee).
- Platform extensions (generic, in the established style): `OwnerScope` gains the `goal` variant (the `workspace` variant was added by MKT-004 the same way); `validation.ts` gains `numberField`, `arrayField`, `optionalArrayField`, `objectField`, `isoDateField` — all generic helpers with unit tests, no goal-specific logic in platform code.

### 4. Policy decisions (recorded honestly)

1. **Goal lifecycle states are an implementation decision**: the frozen `state-machines.md` defines no Goal machine. `draft/active/achieved/abandoned` follows GOAL-001 ("goal lifecycle"), the terminal-immutability convention (AGENTS.md: append-oriented records) and architecture.md §7 ("Goal is not a workflow" — hence business-intent states only, no execution states).
2. **Workspace scope is immutable once set** (including NULL ⇄ set): scope is durable identity; re-scoping is a new goal. Stronger than strictly required (a within-Client move would not cross the hard boundary) — chosen for auditability and a simpler security story.
3. **No `deleted` tombstone for goals** (unlike clients/workspaces): terminal business outcomes (`achieved`/`abandoned`) already provide irreversible history; identifier hygiene is covered by Client tombstones cascading to uniform 404s at the ownership boundary. The DB FK still cascades on a hard client DELETE.
4. **Evidence standard** (architecture.md §7 "where applicable") is deferred to the `/evidence` authority (EVID-001, later Work Item) — not modeled here to avoid pre-empting that authority. **Owner** is modeled as server-derived scope + provenance (`created_by`), not a caller-suppliable mutable field ("ownership is server-derived").
5. **Strategy/plan content** is explicitly NOT a separate authority (implementation-clarifications-v1.2: "no separate Strategy authority in v1.2") — a Goal-owned versioned artifact arrives with Playbooks (MKT-007); nothing here pre-structures it.

### 5. Honest limitations

- No downstream references exist yet (Playbooks/Workflows/Executions are later Work Items) — GOAL-AC-02's "cannot silently execute outside its authorized Client scope" is proven at the persistence/authorization/storage layer (uniform 404 before traversal, immutable scope, DB backstops), which is the complete MKT-006 scope.
- Success criteria are validated for **measurable shape**, not for metric-existence (the `/metrics` authority arrives later); the criterion's `metric` is a free-form name.
- The time horizon is advisory metadata; no scheduling semantics exist in MKT-006.
