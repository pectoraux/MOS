## What was built

The transition from the MKT-009 Workflow INSTANCE (lifecycle **intent**) to the EXECUTION (the **actual runtime attempt**): one normalized Execution identity and lifecycle for deterministic, AI, human and extension execution.

- **One normalized identity (EXEC-AC-01).** All four execution kinds create through one surface, one table, one lifecycle machine and one idempotency fence. Execution identity is independent of provider/model/runtime implementation.
- **The frozen lifecycle.** Eleven states, fourteen legal edges — `CREATED → QUEUED → STARTING → RUNNING` with `PAUSING → PAUSED → RUNNING` returns; `SUCCEEDED`/`FAILED`/`CANCELLED` terminal and immutable (EXEC-AC-02); `UNKNOWN` never-success, **non-terminal**; `UNKNOWN → RECONCILING → SUCCEEDED | FAILED | UNKNOWN`. The machine is enforced edge-for-edge in code (`EXECUTION_TRANSITIONS`) AND in the database (the `execution_transition_legal` predicate + row/history triggers, migration 011).
- **Task linkage as reference data.** An execution links to its logical Task through `(workflow_instance_id, node_id)` coordinates or an explicitly declared external request (`implementation-contract` §7). Per the frozen dependency matrix — `/executions ──→ /workspaces, /policies, /credentials, /audit` and `/workflows ──→ … /executions …` — the linkage columns carry **no FK into the workflow tables** and the module imports no `/workflows` API: `/executions` records the references; the workflow engine (MKT-011+) that composes both authorities owns their consistency.
- **Runtime resource acquisition.** The immutable `runtime_class` declaration from the frozen §9 list (`pooled-worker`, `ephemeral-sandbox`, `persistent-sandbox`, `dedicated-runtime`) plus the durable **sandbox lease** (below).
- **§8 idempotency.** Every create carries a logical idempotency key whose uniqueness the **database** enforces — `UNIQUE (workspace_id, idempotency_key)` — with a create fingerprint so a duplicate converges (200, `replayed=true`, same identity, one audit row) while a key reused for a different command is a 409 (EXEC-AC-03). Transitions carry the same fence per execution on the append-only history.
- **§24 retry classification and the retry gate.** Every transition into `failed` must declare `safe | unsafe`; the classification is recorded set-once on the execution row and on the transition row (DB-enforced). A **retry** is a new attempt row of the same linkage (`attempt_number = prior + 1`, linkage/kind/runtime inherited, `retry_of_execution_id` provenance — no second logical Task identity), permitted **only** from a terminal FAILED + `safe` prior. UNKNOWN is refused with the reconciliation instruction (never automatically retryable); in-flight, succeeded and cancelled priors are refused. The `(retry_of_execution_id, attempt_number)` partial UNIQUE fence guarantees one deliberate next attempt per prior even under concurrent duplicate retries.
- **UNKNOWN/reconciliation.** UNKNOWN is never success; it resolves only through the same single transition port (`unknown → reconciling → succeeded | failed | unknown`), preserving the same execution identity, possibly concluding back in `unknown` (reconcilable again later). Reconciliation decisions may carry an `evidenceRef` — an opaque authoritative external-evidence reference, shape-fenced to reconciliation decisions at the route, module and DB layers.
- **Applied-transition history integrity (the audit erratum correction).** A recorded transition is the record of a decision that **was applied**: the `execution_transitions_legal` trigger resolves the target execution row with `SELECT … FOR UPDATE` (concurrency-safe; the authorized transition path already holds that row lock — lock → record → apply → commit — so the trigger adds no second authority) and rejects any history row whose `from_status` does not equal the execution's durable current status. A syntactically legal pair (`created → queued`) can no longer be fabricated into the ledger against a stale `from_status`, even by direct SQL.
- **The sandbox lease (implementation-contract-v1.2.md §1 / tenant-runtime-v1.2.md).** The lease carries `sandbox_lease_id + sandbox_id + execution_id + client_id + workspace_id` (immutable), lease state/version, and expiry/recovery metadata. The database enforces **one active lease per sandbox** (the strict v1.2 concurrency invariant — the selected invariant, since no sandbox contract declaring safe concurrency exists before MKT-012) and one active lease per execution. Acquisition is concurrency-safe and idempotent (same-key replays converge; cross-execution contention is settled by the partial unique index). Release is idempotent and **never terminalizes the execution** — the release path performs no execution-status write and returns the unchanged record as proof. A stale (expired) lease is reclaimed through the same release operation; the worker/outbox automation of that recovery arrives with MKT-011. There is **no sandbox entity** — the sandbox lifecycle authority is MKT-012, and `execution_id` is never sandbox identity.
- **Boundary policy** (mirroring MKT-008/009): create and transitions **into** running are new use (ACTIVE workspace/client/agency required); runtime bookkeeping, control recording, UNKNOWN recording, reconciliation, terminal recording and cancellation are always available — history keeps being recordable and cancellation is never blocked by a disabled boundary.
- **Uniform tenant posture.** Canonical owner resolution (execution → workspace → client → agency) before authorize/validate/execute; foreign/unknown identifiers are indistinguishable on every route (including foreign lease ids under an execution); operators read but never mutate (403). Audit rows carry the execution-scoped tenant scope and correlation; replays converge to one audit row.

## Policy decisions (documented, not self-invented architecture)

1. **The effective Execution machine is the v1.2 layer.** `state-machines.md` (v1.1, frozen) plus `state-machines-v1.2.md` — which "supersedes conflicting Execution/Sandbox semantics in v1.1" — compose into the eleven-state/fourteen-edge machine implemented here. The v1.1 base already contains every edge except the RECONCILING pair; v1.2 adds `UNKNOWN → RECONCILING → …` and states UNKNOWN is non-terminal. No conflict was invented away: the base diagram's "UNKNOWN is terminal for the attempt outcome **until** an explicit reconciliation operation" is exactly the v1.2 refinement.
2. **No FK from executions to workflow tables** — a direct consequence of the frozen dependency direction (the same direction the workflows module itself documents: "the transitionWorkflowInstance operation IS the authorized workflow command port future /executions and /extensions callers must target"). Storage-level coupling would invert the frozen matrix.
3. **Retry inherits linkage/kind/runtime_class** — a retry is the same work re-attempted; changing the execution's requirements is a new logical execution, not a retry.
4. **One active lease per execution** — the frozen invariant is sandbox-side ("only one active lease may control a Sandbox"); the execution-side single-active-lease is the selected conservative invariant for MKT-010 (one runtime environment per attempt at a time), relaxable by MKT-012 if a declared runtime contract requires concurrent environments.
5. **Strict sandbox concurrency** — no sandbox contract exists that declares safe concurrency (that is MKT-012's authority), so the selected DB-enforced invariant is exactly one active controller per sandbox.
6. **`expiresAt` is recovery metadata, not enforced scheduling** — a lease may be recorded with an already-past expiry (immediately stale, reclaimable); interpreting/enforcing expiry against the clock is runtime policy (MKT-011).
7. **Lease release is tenant-authorized at any time** — the owning tenant may release its own lease whenever it chooses; releasing an *expired* lease is the deterministic stale-recovery path available before the MKT-011 worker/outbox automation.
8. **`evidenceRef` is an opaque reference** — reconciliation evidence is recorded through this bounded reference and resolves against the `/evidence` authority when it exists (MKT-013); the reconciler never fabricates evidence (v1.2 §2).
9. **HTTP response codes for idempotent creates/acquisitions**: 201 fresh, 200 replayed — "Created" only when a row was created.

## The MKT-010 audit erratum and its correction

The Architect's independent review (recorded in `spec/errata/MKT-010-history-ledger.md` and the PR #19 review) found that the original `execution_transitions_legal` trigger validated only that `(from_status, to_status)` was a legal frozen-machine edge — a direct-SQL writer could insert a **fabricated-but-legal** history row whose `from_status` did not match the execution's durable status (e.g. recording `created → queued` while the execution was actually `running`). The correction, applied in place to migration 011 (unmerged branch — no durable environment had applied it):

1. The history trigger now resolves the target execution's current durable status with `SELECT status … FROM executions WHERE execution_id = NEW.execution_id FOR UPDATE` — concurrency-safe, sharing the authorized transition path's row lock (that path locks the execution row **before** recording history and applies the status change in the same transaction, so the trigger's lock acquisition is re-entrant for it and introduces no second authority).
2. A history row whose `from_status` does not equal the resolved durable status is rejected (`fabricated applied transition rejected`), as is a row for an unknown execution.
3. Regression proofs added: the direct-SQL fabricated-history rejection (two stale-but-legal pairs + unknown execution), the consistency predicate's positive case (a matching `from_status` records — the DB enforces exactly the erratum's predicate, never more, mirroring the row-level machine backstop's posture), the normal application transition still succeeding under the corrected trigger, the append-only history re-assertions, and the deterministic no-TOCTOU race (a racing fabricated insert serialized behind the authorized transaction's held row lock is judged against the **post-commit** status).
4. A static architecture assertion proves the backstop exists in the migration (FOR UPDATE resolution + the from_status comparison + the rejection).

No change to the frozen state machine, the execution authority, or the module dependency direction.

## Honest limitations (deliberately out of scope)

- **No execution engine.** No dispatch, no queue consumption, no worker assignment, no node-instance bookkeeping, no input/output payloads, no telemetry, no automatic retry orchestration. Those are the pooled worker authority (MKT-011); the retry here is the explicitly commanded, classification-gated new attempt. `/workflows` does not call `/executions` yet — that composition arrives with the engine.
- **No sandbox lifecycle.** There is no sandbox entity, no `REQUESTED → PREPARING → READY` machine, no lease-expiry automation (the stale lease is reclaimed through the explicit release). MKT-012 owns these; MKT-010 owns only the lease relationship.
- **No deployment/participant/policy-snapshot/input-output/evidence/telemetry columns** on executions (architecture.md §11's full containment list is satisfied progressively by later work items — the same progressive posture as MKT-008/009). The workflow definition version is reachable through the linked instance's explicit pin (MKT-009); duplicating it unverifiably would invite inconsistency.
- **No pagination** on the workspace execution list (consistent with every prior list surface).
- **Reconciliation is a two-step protocol through the single transition port** (`unknown → reconciling`, then the decision), not a separate one-shot operation; this keeps ONE mutation port (the same structural rule the MKT-009 audit confirmed) while the machine records the RECONCILING state explicitly. The reconciliation evidence reference rides the decision transition.
- **Task linkage consistency is the authorized caller's contract** (see policy decision 2): MKT-010 records and fences the linkage shape; it cannot and must not verify that the referenced workflow instance exists or that the node belongs to its pinned definition.
- **Direct-SQL history writes with a *matching* `from_status` remain physically recordable** (the erratum's predicate is `history.from_status == execution.status`, not a writer ban — the same posture as the row-level machine backstop, which permits the legal direct-SQL status change): a writer who records a consistent row without applying it to the execution row in the same transaction leaves the ledger describing one more transition than the row's status reflects. The trigger cannot distinguish "record-then-apply in one transaction" from "record-only" at insert time without becoming the applier itself; that reorganization is outside the erratum's required correction. The authoritative writer is the application path, whose record→apply is atomic.
- **The same consistency backstop does not yet exist for `workflow_instance_transitions`** (migration 010, merged with MKT-009): its history trigger validates the legal edge but not `from_status == instance.status`. That table belongs to MKT-009's already-merged surface and migration 010 is checksummed-immutable on `main`; the equivalent correction there needs its own migration and is the Architect's call (reported on PR #19).
