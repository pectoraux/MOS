# MKT-004 Acceptance Contract — Workspace Boundary

**Work Item:** MKT-004
**Architecture:** v1.4 frozen
**Purpose:** make the Workspace boundary explicit for implementation and review without changing the frozen architecture.

## Scope

Implement Client-scoped Workspace persistence and authorization inside the existing `/workspaces` authority. Workspace is an organizational/execution boundary inside exactly one Client; it may not weaken Client hard isolation and it is not an independent tenant/security boundary.

## Required behavior

1. Every Workspace has one immutable `client_id` derived from the canonical Client owner context.
2. Workspace authorization resolves the Client owner before any dependent Workspace traversal.
3. A Workspace identifier is never itself an authorization credential.
4. Cross-Client Workspace access is denied before dependent traversal or external access.
5. Caller-supplied `client_id`, `agency_id`, `workspace_id` and equivalent authority fields are rejected or ignored only where the frozen API contract explicitly requires derivation; for mutations, authority fields must be rejected.
6. Authorization is resolved from durable Client/Agency membership state and Workspace state, not process-local cache authority.
7. Workspace lifecycle changes do not rewrite historical Client-owned records.
8. Concurrent Workspace uniqueness/lifecycle operations are DB-fenced/CAS-protected where applicable.
9. No second tenant, authorization, workflow or execution authority is introduced.

## Negative security matrix

The implementation must prove at minimum:

- anonymous caller → denied;
- user from another Agency → denied;
- Agency member without sufficient role → denied;
- Workspace from another Client → denied without child/dependent lookup;
- forged `agency_id`, `client_id`, `workspace_id`, user/role/platform authority headers or body fields → cannot widen scope;
- stale/revoked membership → denied after membership change and after API restart;
- disabled/deactivated Client → Workspace access follows Client policy and cannot resurrect Client authority;
- deleted/tombstoned Client → Workspace cannot be used to resurrect access.

## Concurrency

Prove duplicate Workspace identity/name constraints (where specified by implementation contract) are database-enforced and concurrent mutable updates use version/CAS or equivalent database serialization with deterministic conflict behavior.

Required integration evidence must use the real PostgreSQL-backed implementation and real API/process boundaries already established by MKT-001.

## Explicit non-goals

- No Goals/Playbooks/Workflow/Execution implementation.
- No new tenant model.
- No separate Workspace permission engine.
- No provider integrations.
- No frontend-only authorization.
- No modifications to frozen architecture documents.
