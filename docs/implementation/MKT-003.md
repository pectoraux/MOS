# MKT-003 — Client tenancy and hard isolation: implementation record

**Work Item:** MKT-003 (issue #9) · **Architecture:** v1.4 (frozen) · **Base:** `ce316d0` (MKT-002 merged)

## What was implemented

- **Migration `003_clients.sql`** — `clients` table with server-generated immutable `client_id`, NOT NULL `agency_id` FK (Agency→Client ownership), `name`/`slug`, lifecycle `status` CHECK (`active|disabled|deleted`), `created_by` provenance, `version` CAS, timestamps. DB backstops (implementation-contract §25):
  - **immutability trigger** — `client_id`, `agency_id`, `created_at`, `created_by` can NEVER be reassigned through any UPDATE path (TENANT-AC-02; tenant migration is structurally impossible);
  - **deleted-terminal trigger** — tombstones never resurrect;
  - **partial unique fence** `(agency_id, slug) WHERE status IN ('active','disabled')` — per-tenant slug uniqueness among live clients, race-free under concurrent creation; tombstones do not block slug reuse (new immutable identity).
- **`/clients` module** (authority: Client ownership/isolation) — public contract (`ClientRecord`, `ClientStatus`, `CLIENT_TRANSITIONS`, `ClientOwnerContext`, `composeClientOwnerContext`, `ClientsModuleApi`), internal store + module. Dependency matrix respected: `/clients ──→ /agencies, /auth` (imports `/agencies` public only; Principal comes from the platform auth port).
  - `resolveClientOwnership(clientId)` — **the canonical owner resolution** (MKT-003-AC-01): live client row + owning agency → `ClientOwnerContext` `{scope:{kind:'client',agencyId,clientId}, client, agency, resolvedAt}`, derived fresh from durable state on every call. Tombstones never resolve.
  - CAS lifecycle/profile mutations in row-locked transactions with the frozen transition table (`active⇄disabled→deleted`, deleted terminal).
- **6 routes** (`src/api/clients-routes.ts`) following the §23 pipeline (authenticate → resolve canonical owner → authorize → strict validation with forbidden authority fields → server-derived fields → execute → correlated emit → normalized result):
  - `POST /api/agencies/:agencyId/clients` (owner|admin|platform admin; agency must be active)
  - `GET /api/agencies/:agencyId/clients` (any active member; live clients only)
  - `GET /api/clients/:clientId` (member of the OWNING agency)
  - `GET /api/clients/:clientId/ownership-context` (read-only canonical owner context — AC-01 evidence surface)
  - `PATCH /api/clients/:clientId/profile` (owner|admin|platform admin, CAS; slug immutable)
  - `PATCH /api/clients/:clientId/status` (owner|admin|platform admin, CAS + transition table)
- **`requireClientAccess`** (authorize.ts): ownership resolution FIRST (uniform 404 for unknown/deleted), then membership authorization against the OWNING agency — see policy below.

## Policy decisions (implementation choices within the frozen contract)

1. **Cross-tenant posture — uniform 404.** A caller with no membership in the OWNING agency receives the SAME `NOT_FOUND` 404 as for an unknown identifier: the Client is the hard security/data boundary (architecture.md §2), so foreign identifiers must not act as an existence/traversal oracle (TENANT-AC-04). Intra-tenant failures stay 403 (suspended membership / wrong role), mirroring `/agencies`. This hardens the MKT-002 disclosure that agencies (commercial tenants) use 404/403 while reserving uniform 404 for the Client boundary.
2. **Platform administrators and the internal service principal** retain platform-operator access to Client routes, mirroring `requireAgencyAccess` semantics from MKT-002 (the boundary being enforced is Agency↔Client cross-tenant isolation, not platform↔tenant).
3. **Role model:** create/update/lifecycle = `agency_owner|agency_admin` (+ platform operators); read/list = any ACTIVE member — including `client_collaborator` and `human_agent`, whose client-scoped semantics arrive with this Work Item per the frozen role registry descriptions.
4. **Disabled Client:** blocks profile mutations (409) and any new authorized use; reads remain visible to members (history is not rewritten — MKT-003-AC-03); re-enable is the explicit lifecycle path. **Deleted Client:** terminal tombstone — every route 404s, direct DB resurrection raises, slug reusable only by a NEW identity.
5. **Disabled Agency:** blocks new client creation (409, mirroring MKT-002 membership-add policy); existing client reads remain visible.
6. `created_by` is provenance only — never read for authorization.

## Architectural integrity

- No frozen architecture document modified (diff over `spec/`, `docs/architecture`, `docs/handoff`, `AGENTS.md`, `README.md`, PR template = empty).
- No second tenant/authorization authority: Client ownership lives only in `/clients`; membership/role authorization stays in `/agencies`; `requireClientAccess` composes the two into ONE canonical owner context per operation.
- No Client-scoped operation bypasses canonical owner resolution: every client route resolves ownership in step 2 (mutation pipeline) or authorize (query pipeline) before any dependent data access; `resolveClientOwnership` is the only entry to client-scoped work.
- No Workspace persistence/authorization (MKT-004 untouched: forged `workspaceId` fields are rejected as unknown/authority fields — 422).
- No provider SDKs; `pg` remains the only runtime dependency; no new dependencies.
- Authorization derives from durable state on every call — no process-local cache (proven across an API restart).

## Honest limitations / disclosures

- No child/dependent domain objects exist yet (Workspace is MKT-004), so "rejection before dependent traversal" is proven at the boundary itself: foreign identifiers fail at ownership resolution with zero emitted material-mutation records and zero durable-state changes. Future Client-scoped modules must consume `ClientOwnerContext` — this is the seam.
- Client status transitions are single-row CAS; there is no cross-row invariant (unlike the MKT-002 last-owner guard), so no deadlock-mapping is needed; concurrent same-version transitions deterministically yield exactly one winner.
- Existence-visibility posture: foreign Client → 404 uniform (hard boundary); agency-level routes keep the MKT-002 404/403 split (agency exists + no membership → 403). Both are documented, deliberate postures.
- No rate limiting on repeated 404 probes (not required by any AC; platform-level hardening item).
- Listing returns all live clients of the caller's agency; pagination/filtering is out of scope for this Work Item.
